# 学情画像设计

## 1. 设计目标

学情画像是系统个性化能力的核心依据。它不能只服务某一门课程，也不能只作为页面展示卡片存在，而应该成为 AI 对话、资源生成、学习路径、资源推荐、练习评估和学习闭环的共同上下文。

系统需要支持：

* 用户选择课程后，围绕课程学习状态构建课程画像；
* 用户不选择课程时，仍能基于全局画像和当前会话进行通用学习；
* 同一用户学习多门课程时，课程画像彼此隔离，但可通过跨课程分析发现共性短板；
* 自然语言对话、学习行为、测验表现、资源使用、用户纠偏都可以成为画像证据；
* 画像随学随新，但更新需要有来源、置信度和作用范围，避免数据污染。

---

## 2. 核心设计结论

学情画像不能设计成“单课程六维画像”，而应设计成 **多层动态学习画像**。

```text
同一个用户
  ├─ 全局学习画像 Global Profile
  ├─ 多课程画像 Course Profiles
  │    ├─ 深度学习课程画像
  │    ├─ 机器学习课程画像
  │    ├─ 高等数学课程画像
  │    └─ 其他课程画像
  ├─ 当前会话画像 Session Profile
  └─ 跨课程画像 Cross-course Profile
```

不同层级解决不同问题：

| 画像层级 | 解决的问题 | 是否绑定课程 |
|---|---|---|
| 全局学习画像 | 用户是谁、怎么学、长期目标是什么 | 否 |
| 课程画像 | 用户在某门课中学到哪里、哪里薄弱 | 是 |
| 会话画像 | 当前这次对话正在做什么、是否临时任务 | 可选 |
| 跨课程画像 | 多门课程之间的共性短板、前置知识关联和能力迁移 | 否，但来自多课程证据 |

---

## 3. 全局学习画像

全局画像描述用户跨课程长期稳定的学习特征。它在无课程通用学习场景下直接生效，在有课程场景下作为课程画像的基础背景。

### 3.1 适用场景

* 用户未选择课程时的普通学习对话；
* 用户进行通用学习规划；
* 用户跨课程学习；
* 用户生成通用资料；
* 用户进入任意课程后的默认个性化；
* 用户未指定课程但希望系统记住学习偏好。

### 3.2 推荐维度

| 维度 | 用户侧解释 | 示例 |
|---|---|---|
| 专业背景 | 我是什么专业，已有基础是什么 | 计算机专业，Python 熟悉，数学一般 |
| 长期学习目标 | 我整体想达到什么能力 | 做 AI 项目、通过考试、准备求职 |
| 认知风格 | 我更容易怎么理解知识 | 代码实践型、图解型、类比型、公式推导型 |
| 学习节奏 | 我适合多快学、每次学多少 | 碎片化学习、每天 30 分钟、稳步推进 |
| 资源偏好 | 我喜欢什么学习资料 | 代码案例、图解讲义、自测题、视频脚本 |
| 通用能力短板 | 不绑定具体课程的弱项 | 抽象概念理解慢、数学符号敏感、公式推导弱 |
| 表达偏好 | AI 应该怎么和我说话 | 少术语、先结论后解释、多举例 |
| 学习习惯 | 我常用什么方式学习 | 先问概念，再要例子，再做题 |

### 3.3 示例

```json
{
  "userId": "u_001",
  "scope": "global",
  "major": "计算机科学与技术",
  "longTermGoals": ["完成深度学习课程项目", "具备 AI 项目实践能力"],
  "cognitiveStyle": {
    "label": "代码实践型",
    "confidence": 0.82,
    "evidenceCount": 9
  },
  "resourcePreference": ["代码实验", "图解讲义", "自测题"],
  "pace": "碎片化稳步推进",
  "generalWeaknesses": ["公式推导理解慢", "矩阵维度敏感"],
  "updatedAt": "2026-06-05T00:00:00Z"
}
```

## 4. 课程画像

课程画像描述用户在某一门课程中的具体学习状态，必须绑定 `courseId`。

### 4.1 适用场景

* 用户选择课程进入 `/dashboard`；
* 用户在 `/learning-path` 学习某个节点；
* 用户做某门课程的测验；
* 用户基于某门课程生成讲义、题库、代码实验；
* 用户查看某门课程资源大厅；
* 系统为课程内节点生成补救建议。

### 4.2 推荐维度

| 维度 | 用户侧解释 | 示例 |
|---|---|---|
| 课程知识基础 | 我在这门课里会什么 | Tensor 操作基本可用 |
| 当前课程掌握度 | 我这门课学到什么程度 | 掌握度 62% |
| 当前学习节点 | 我现在学到哪里 | 1.1 数据操作 |
| 课程易错点 | 我在这门课哪里容易错 | 矩阵维度、广播机制、卷积输出尺寸 |
| 课程学习目标 | 我学这门课的目的 | 完成课程项目、通过阶段测验 |
| 课程资源偏好 | 这门课适合我用什么资源 | PyTorch 实验、错题补救卡 |
| 课程学习路径状态 | 下一步该学什么 | 自动求导 → 线性回归 |
| 课程测评表现 | 练习和测验结果 | 概念题较强，代码题偏弱 |

### 4.3 示例

```json
{
  "userId": "u_001",
  "scope": "course",
  "courseId": "deep-learning",
  "courseName": "深度学习",
  "currentNode": "卷积神经网络",
  "mastery": 0.62,
  "weakPoints": ["特征图尺寸", "卷积核参数", "矩阵维度"],
  "resourcePreferenceInCourse": ["PyTorch 实验", "图解讲义"],
  "assessmentSummary": {
    "conceptScore": 0.76,
    "codingScore": 0.48,
    "transferScore": 0.52
  },
  "updatedAt": "2026-06-05T00:00:00Z"
}
```

### 4.4 课程画像不能覆盖全局画像

课程画像中的弱点默认只属于该课程。例如用户在深度学习课程中经常犯矩阵维度错误，不能直接推断为用户所有课程都存在同类问题。

只有当类似证据在多门课程中反复出现，才可以上升为全局短板或跨课程画像。

```text
深度学习：矩阵维度错误
机器学习：矩阵运算错误
线性代数：矩阵乘法错误
  ↓
跨课程画像：矩阵运算和维度理解存在共性薄弱点
  ↓
全局画像候选：数学符号和矩阵运算敏感
```

## 5. 会话画像

会话画像描述当前对话的临时上下文。它生命周期短，但对本次 AI 回答和资源生成非常关键。

### 5.1 适用场景

* 用户没有选择课程，但当前对话有明确主题；
* 用户临时补充偏好，例如“这次讲简单点”；
* 用户上传临时资料；
* 用户进行一次性资源生成；
* 用户从深链进入某个资源任务；
* 用户在一次对话中从问答转为生成。

### 5.2 推荐维度

| 维度 | 说明 |
|---|---|
| 是否选中课程 | 有课程 / 无课程 |
| 当前主题 | 当前问题涉及什么知识方向 |
| 当前任务类型 | 问答、规划、资源生成、测验、总结 |
| 当前临时目标 | 本次对话想完成什么 |
| 当前资源需求 | 是否需要讲义、题目、代码、思维导图 |
| 当前上下文来源 | 全局画像、课程画像、用户临时说明、上传文档 |
| 临时偏好 | 本轮会话用户临时要求的讲解风格或输出格式 |

### 5.3 示例

```json
{
  "conversationId": "c_001",
  "scope": "general",
  "courseId": null,
  "topic": "大模型微调",
  "intent": "学习规划",
  "temporaryGoal": "一周内了解 LoRA 微调流程",
  "temporaryPreference": "偏项目实践，少公式",
  "expiresAt": "conversation_end"
}
```

## 6. 跨课程画像

跨课程画像用于识别多门课程之间的共性能力问题、前置知识关联和迁移能力。

### 6.1 适用场景

* 用户同时学习多门课程；
* 某门课程的薄弱点来自另一门课程的前置知识；
* 系统需要推荐跨课程补救资源；
* 用户在多门课程中表现出相似错误模式。

### 6.2 示例

```text
高等数学：链式法则薄弱
深度学习：反向传播理解困难
机器学习：梯度下降方向理解不稳
  ↓
跨课程分析：微积分链式求导是深度学习反向传播的前置短板
  ↓
推荐：生成“链式法则到反向传播”的跨课程补救卡
```

### 6.3 推荐维度

| 维度 | 示例 |
|---|---|
| 共性短板 | 矩阵运算、链式法则、概率理解 |
| 前置知识影响 | 高等数学影响深度学习反向传播 |
| 迁移能力 | 会做例题，但换场景容易卡住 |
| 跨课程推荐 | 补学线性代数中的矩阵乘法 |
| 证据来源 | 来自多门课程测验、错题、对话、资源使用 |

## 7. 画像组合逻辑

系统在 AI 调用前，需要通过 Profile Context Resolver 生成本次有效画像上下文。

### 7.1 有课程场景

```text
最终画像上下文 =
全局学习画像
+ 当前课程画像
+ 当前会话画像
+ 当前学习节点 / 知识点
```

示例：

```json
{
  "scope": "course",
  "courseId": "deep-learning",
  "globalProfile": {
    "major": "计算机",
    "cognitiveStyle": "代码实践型",
    "resourcePreference": ["代码案例", "图解讲义"]
  },
  "courseProfile": {
    "currentNode": "卷积神经网络",
    "weakPoints": ["特征图尺寸", "卷积核参数"],
    "mastery": 0.62
  },
  "sessionProfile": {
    "intent": "生成自测题"
  }
}
```

### 7.2 无课程场景

```text
最终画像上下文 =
全局学习画像
+ 当前会话主题
+ 用户本轮问题
```

示例：

```json
{
  "scope": "general",
  "courseId": null,
  "globalProfile": {
    "major": "计算机",
    "cognitiveStyle": "代码实践型",
    "resourcePreference": ["代码案例", "图解讲义"]
  },
  "sessionProfile": {
    "topic": "梯度下降",
    "intent": "概念解释"
  },
  "courseProfile": null
}
```

### 7.3 从学习路径进入

```text
最终画像上下文 =
全局学习画像
+ 当前课程画像
+ 当前路径节点
+ 当前资源类型
```

## 8. 画像写入规则

画像更新必须先判断上下文范围。

```text
用户行为
  ↓
判断当前上下文
  ↓
是否选中课程？
  ├─ 是：写入对应课程画像 + 全局画像候选证据
  └─ 否：写入通用学习记录 + 全局画像候选证据 + 会话画像
```

### 8.1 写入课程画像

适合写入课程画像的证据：

* 课程测验结果；
* 课程学习路径节点状态；
* 课程资料问答记录；
* 绑定课程的资源使用记录；
* 课程内错题归因；
* 课程内用户明确表达的学习目标。

### 8.2 写入全局画像

适合写入全局画像的证据：

* 用户明确说明专业、长期目标、学习偏好；
* 多次对话中稳定出现的认知风格；
* 多门课程共同出现的能力短板；
* 用户在个人设置中主动确认或纠正的偏好。

**冷启动引导模式的直写路径**：

引导模式下（冷启动或 `force_onboarding`），`workflow.stream_chat` 通过 `_parse_onboarding_structured_answer` 解析 LLM 结构化 JSON 返回的 `dimensions`，直接调用 `LearningProfileRepository.apply_dimensions_to_global` 写入全局画像，`source_type="onboarding_llm"`，`method="llm_onboarding"`。此路径跳过 `ProfileExtractor`（由 `_node_profile` 检测 `onboarding_dimensions_written` 标记），避免重复抽取。预设 chip 点击则通过 `OnboardingService.apply_preset_chip` 直接写画像，`source_type` 标记为 onboarding 预设。

### 8.3 写入会话画像

适合写入会话画像的证据：

* 本轮临时要求；
* 当前主题；
* 当前任务意图；
* 当前上传文档；
* 本次对话中的临时目标。

### 8.4 防止画像污染

不允许：

* 无课程对话直接写入某门课程画像；
* 某门课程的单次错误直接上升为全局弱点；
* 临时偏好覆盖长期偏好；
* 低置信度推断直接影响高风险推荐；
* 用户已纠正的画像继续被旧证据覆盖。

## 9. 画像抽取

画像抽取不应依赖单纯关键词规则。当前项目已经具备 `ProfileExtractor`、`LearningProfileRepository`、`CourseConcept`、`ProfileEvidence` 和模型网关，因此推荐主路径是：

```text
对话 / 测评 / 资源使用 / 用户纠偏
  ↓
本地候选抽取
  ├─ 技术实体候选：LoRA、反向传播、矩阵维度、PyTorch、BatchNorm
  └─ 课程概念表匹配：CourseConcept.title / code / meta_json aliases
  ↓
schema-based LLM 信息抽取
  ├─ 学情画像维度：薄弱知识点、资源偏好、学习目标、认知风格、临时偏好
  ├─ 技术实体确认
  └─ 课程概念确认
  ↓
Pydantic schema 校验 + 作用范围校验
  ↓
写入全局画像 / 课程画像 / 会话画像 / 全局候选证据
  ↓
规则抽取仅作为失败兜底
```

### 9.1 抽取输入

| 来源 | 可抽取内容 | 写入倾向 |
|---|---|---|
| 用户消息 | 技术实体、薄弱点、目标、偏好、临时要求 | 课程画像或全局画像 |
| AI 回答摘要 | 本轮解释对象、资源形式、可能暴露的学习困难 | 证据补充 |
| 当前课程与知识点 | `courseId`、`conceptId`、路径节点 | 课程画像 |
| 课程概念表 | 课程知识点、前置关系、同义词 | 知识点对齐 |
| 测评结果 | 提交后的得分、逐题错因、知识点掌握度、是否需要补救 | 课程画像 |
| 资源使用 | 偏好的资源类型和完成情况 | 资源偏好、学习习惯 |
| 用户纠偏 | 用户确认或否认的画像项 | 最高优先级证据 |

### 9.2 技术实体与课程概念抽取

技术实体抽取负责识别“用户正在谈什么知识对象”，例如：

```text
LoRA、反向传播、链式法则、矩阵维度、广播机制、PyTorch、BatchNorm、自动求导
```

课程概念匹配负责把自然语言中的技术对象对齐到课程建设台维护的 `CourseConcept`：

* 优先匹配 `title`、`code`；
* 支持从 `meta_json.aliases`、`keywords`、`tags` 中读取同义词；
* 匹配结果只作为画像证据，不直接生成画像结论；
* 同一个技术实体可以同时作为课程画像证据和跨课程前置知识候选。

示例：

```text
用户：我不懂 Backprop 的链式法则推导，想要 PyTorch 实验。

技术实体候选：反向传播、链式法则、PyTorch
课程概念匹配：反向传播(backpropagation)
画像候选：
  - weakness：公式推导
  - resource_preference：代码实验
  - cognitive_style：代码实践型
```

### 9.3 schema-based LLM 抽取

LLM 不直接自由生成画像文本，而是必须输出结构化 JSON：

```json
{
  "dimensions": [
    {
      "key": "weakness",
      "score": 42,
      "label": "公式推导",
      "evidence": "用户明确表示不懂反向传播中的链式法则推导"
    },
    {
      "key": "resource_preference",
      "score": 86,
      "label": "代码实验",
      "evidence": "用户希望通过 PyTorch 实验学习"
    }
  ],
  "technical_entities": [
    { "name": "反向传播", "entity_type": "concept", "evidence": "用户提到 Backprop" },
    { "name": "PyTorch", "entity_type": "framework", "evidence": "用户要求 PyTorch 实验" }
  ],
  "matched_concepts": [
    { "code": "backpropagation", "title": "反向传播", "evidence": "命中课程概念别名 Backprop" }
  ]
}
```

后端使用 Pydantic 校验输出：

* `dimensions[].key` 必须属于当前画像范围允许的 key；
* `score` 必须在 0 到 100；
* `label` 和 `evidence` 必须非空；
* 低于最小维度数、JSON 非法、key 不合法时丢弃 LLM 结果；
* LLM 失败后再进入规则兜底。

### 9.4 作用范围校验

抽取结果必须先判断作用范围：

| 当前上下文 | 允许直接写入 | 不允许 |
|---|---|---|
| 无课程对话 | 全局画像、会话画像 | 直接写入某门课程画像 |
| 有课程对话 | 当前课程画像、会话画像、全局候选证据 | 把单次课程弱点直接升为全局弱点 |
| 测评结果 | 当前课程画像 | 直接覆盖用户纠偏 |
| 用户纠偏 | 指定 scope 的画像项 | 被低置信系统推断覆盖 |

课程内抽到的 `weakness`、`resource_preference`、`cognitive_style` 可以写成全局候选证据。只有多课程重复出现，才由跨课程逻辑提升为全局短板。

### 9.5 规则兜底

规则抽取只负责兜底，不作为主力。适用场景：

* 模型网关不可用；
* LLM JSON 不合法；
* LLM 输出字段不满足 schema；
* 当前环境关闭 `PROFILE_LLM_EXTRACTION_ENABLED`。

兜底规则只生成中低置信度证据，例如：

| 规则信号 | 画像候选 |
|---|---|
| “不会 / 不懂 / 推导 / 链式 / 梯度” | `weakness = 公式推导` |
| “矩阵维度 / shape / 广播” | `weakness = 矩阵维度` |
| “代码 / 实验 / PyTorch / notebook” | `resource_preference = 代码实验` |
| “图 / 动画 / 可视化 / 思维导图” | `resource_preference = 图解动画` |
| “自测 / 练习题 / 刷题” | `resource_preference = 自测题` |

### 9.6 外部抽取组件优先级

当前阶段优先使用项目内主路径，不建议为了画像抽取立即引入重型 NLP 依赖。后续如果要增强，可以按以下优先级接入：

| 组件 | 适合用途 | 在本项目中的定位 |
|---|---|---|
| PaddleNLP UIE / Taskflow | 中文 schema 信息抽取 | 可替换或增强 LLM 前的中文结构化抽取 |
| DeepKE / OneKE | 实体关系抽取、知识图谱构建 | 适合抽“高数链式法则 → 深度学习反向传播”的前置关系 |
| GLiNER | 自定义标签 NER | 适合轻量抽技术名词和工具框架 |
| HanLP / LTP | 分词、NER、依存句法 | 适合作为候选词增强，不单独承担画像判断 |

推荐落地顺序：

1. 先稳定 `ProfileExtractor + CourseConcept` 的 schema 抽取主路径；
2. 再把课程建设台中的概念别名、前置关系补齐；
3. 需要抽跨课程前置关系时，再引入 DeepKE / OneKE；
4. 需要离线中文抽取能力时，再考虑 PaddleNLP UIE；
5. HanLP / LTP 仅作为分词和候选增强层。

## 10. 画像证据与置信度

每个画像标签都应有证据记录。

```ts
interface ProfileEvidence {
  id: string
  userId: string
  scope: 'global' | 'course' | 'session' | 'cross_course'
  courseId?: string | null
  dimension: string
  label: string
  sourceType: 'conversation' | 'assessment' | 'resource_usage' | 'path_progress' | 'user_correction'

  confidenceDelta: number
  summary: string
  createdAt: string
}
```

置信度建议分为：

| 置信度 | 含义 | 使用策略 |
|---|---|---|
| 0.00 - 0.39 | 低置信 | 只作为候选，不直接强影响推荐 |
| 0.40 - 0.69 | 中置信 | 可轻量影响回答风格和推荐排序 |
| 0.70 - 0.89 | 高置信 | 可作为个性化主要依据 |
| 0.90 - 1.00 | 用户确认 | 最高优先级，除非用户再次修改 |

## 14. 对话式画像采集交互设计（冷启动引导）

画像抽取的后端管道已经稳定，但第一次接触用户时，交互方式决定了用户对"对话构建画像"的直观感受。如果交互像审讯式问答，即使后端再智能，用户也会觉得是"换皮表单"。本节描述前端冷启动引导方案。

### 14.1 设计原则：刚性骨架 + 柔性交互

```
刚性骨架（后端/Prompt 工程）
  ├─ DB Schema：UserProfile、CourseProfile、ProfileDimension 预设好字段
  ├─ Prompt：system prompt 中指定 dimension key 枚举值
  └─ 推荐引擎：按 knowledge_base / cognitive_style 等固定 key 读取
                    ↓
柔性交互（前端/对话流）
  ├─ 不按字段顺序挨个追问（避免套壳表单感）
  ├─ 将追问嵌入"解决具体学习问题"的服务过程中
  └─ 易错点、学习进度等维度通过后台行为隐式挖掘，不靠问
```

**最高准则**：画像构建是"伴随式成长"的结果，而非"审讯式问答"的产物。字段（Schema）是为后端准备的，自然流畅的痛点解决流程是为学生准备的，两者通过精准的 Prompt 工程解耦。

### 14.2 冷启动检测

```text
用户首次进入工作台
  ↓
前端查询：GET /api/v1/profile?scope=global
  ↓
dimensions 为空 或 有效维度 < 3？
  ├─ 是 → 触发冷启动引导流程（ProfileOnboardingWizard）
  └─ 否 → 直接进入常规对话界面
```

冷启动引导仅在以下情况触发：
- 该用户从未在任何课程中产生过对话；
- 全局画像 `dimensions` 为空或置信度均低于 0.4；
- 前端本地存储中无"已跳过引导"标记。

### 14.5 3 轮封顶原则

冷启动弹窗中最多进行 **3 轮**"点击/输入"交互，之后即使画像只有部分维度有值，也必须主动关闭弹窗，进入主界面：

```text
前端状态机：
  phase: 'idle' | 'active' | 'closing'
  round: 0 | 1 | 2 | 3
  completedDimensions: string[]

  round >= 3 → phase = 'closing'
    → AI 发送收尾话术：
      "我已为你建立初步画像，剩余维度我会在你后续做题和看视频中
       悄悄学习哦！现在开始你的学习之旅吧！"
    → 关闭弹窗，进入 AiDialogueCabin 常规界面
```

此设计完美诠释"随学随新"——不是"把 6 个维度问完了再放我进去"，而是"先完成核心维度，剩余维度在后续自然交互中持续累积"。

### 14.6 Text Injection 模式（点击即文本注入）

这是区分"真智能"与"假对话"的关键技术实现。前端点击卡片时，**不允许直接传结构化 code 给后端**：

```text
❌ 错误做法：
  前端 → 后端：{ "code": "data_science" }
  // 大模型收到的是 code，无法进行语义理解，退化为硬编码映射

✅ 正确做法（Text Injection）：
  前端 → 输入框填充文字 → 自动点击发送
  后端 → 大模型收到的消息：{ "content": "我选数据科学" }
  // 大模型始终处理自然语言，走统一 LLM 语义理解管道
```

引导态提供两条提交路径：

- **预设 chip 点击**：chip `payload` 为完整自然语言句子，前端 `submitPresetChip` 提交，后端 `OnboardingService.apply_preset_chip` 直接写画像 + 返回模板话术，**不走 LLM**，保证低延迟。
- **自由输入**：前端 `submitFreeInput` 触发 WebSocket 流式请求，后端 `workflow.stream_chat` 注入 `build_onboarding_system_prompt` 约束 LLM 返回结构化 JSON（`user_visible` + `dimensions` + `chips`），缓冲解析后 `user_visible` 打字机展示、`dimensions` 直写画像、`chips` 注入下一轮。

```typescript
// 路径 A：预设 chip 点击（Text Injection，不走 LLM）
function handleChipClick(text: string) {
  setDraft(text);                       // 1. 填充输入框（用户可见）
  setTimeout(() => submitPresetChip(), 100); // 2. 自动提交预设 chip
}

// 路径 B：自由输入（走 LLM 结构化 JSON 返回）
function handleFreeInputSubmit(text: string) {
  submitFreeInput(text);                // WebSocket 流式 LLM
}
```

当用户在输入框主动打字时，系统自动隐藏当前快捷卡片，且告诉大模型"用户主动输入的内容权重最高，覆盖之前的点击选项"，体现对用户自主意愿的尊重。

### 14.7 后端数据库设计补充

冷启动引导不需要新增表，复用现有 ProfileEvidence 和 ProfileDimension：

```typescript
// 新增前端引导状态（localStorage 或 UserSetting meta_json）
interface OnboardingState {
  skipped: boolean;                   // 是否已跳过引导
  completedAt: string | null;         // 引导完成时间
  rounds: {
    round: number;
    question: string;
    answer: string;
    extractedDimensions: string[];     // 本轮抽取到的维度 key
  }[];
}
```

后端只需新增一个轻量引导接口，或复用现有对话流：

```text
方案 A（已实现，走现有 WebSocket 对话流）：
  WebSocket /ws/ai/{conversation_id} 在 handle_message 前检测引导条件
  → 命中（is_general_learning 且 onboarding_history/force_onboarding/is_cold_start）
  → 走 workflow.stream_chat 流式输出
  → stream_chat 内部：cold_start 检测 → 注入 build_onboarding_system_prompt
  → LLM 返回结构化 JSON（user_visible + dimensions + chips）
  → _parse_onboarding_structured_answer 解析
  → user_visible 打字机 yield / dimensions 直写画像（source_type="onboarding_llm"）
  → onboarding_update 事件 + done 帧（meta.onboarding）
  → _node_profile 检测 onboarding_dimensions_written 跳过 extractor
  → 无需新增 endpoint

方案 B（独立引导接口，未采用）：
  POST /api/v1/profile/onboarding/start → 返回第1轮问题 + 快捷卡片选项
  POST /api/v1/profile/onboarding/step  → 提交本轮回答，返回下一轮
```

预设 chip 点击路径不走 WebSocket，由前端 `submitPresetChip` 调用 `OnboardingService.apply_preset_chip` 直接写画像 + 返回模板话术，保证低延迟。

### 14.8 Prompt 控制要点

在 system prompt 中必须明确以下约束，防止 LLM 在冷启动阶段过度追问：

```
1. 冷启动阶段只抽取明确出现的维度，不追问未提及字段；
2. 已获取字段清单（由后端传入手）严禁重复提问；
3. 优先询问对学习路径规划影响最大的维度（知识基础、学习目标），
   而非边缘维度（学习习惯、表达偏好）；
4. 用户主动输入的内容权重高于点击卡片的选择；
5. 3 轮后自动结束引导，即使维度不全；
6. 剩余维度标注为 "待观察" 或留空，在后续交互中持续抽取。
```

### 14.9 实施优先级

| Phase | 内容 | 工作量 | 依赖 |
|---|---|---|---|
| **P0** | 冷启动检测 + 3轮状态机 + QuickReplyChips 基础组件 | 2-3天 | 现有 ProfileExtractor、AiDialogueSuggestionPanel |
| **P1** | Text Injection 模式 + 自动隐藏卡片 | 1天 | P0 |
| **P2** | 右侧 ProfileTagCloud 实时联动 + 拼图进度 | 2天 | P0 |
| **P3** | 毛玻璃全屏弹窗 + 入口动画 + 粒子效果 | 2-3天 | P0-P2 |

### 14.10 答辩展示建议

该方案在演示时具备以下视觉亮点：

1. **冷启动 vs 传统表单对比**：展示一张传统 6 维度调查问卷截图，再展示 3 轮沉浸式对话，形成强烈对比；
2. **Text Injection 抓包演示**：用开发者工具 Network 面板展示点击卡片时发送的是自然语言而非结构化 code；
3. **右侧标签实时飞入**：屏幕录制展示用户每点击一次卡片，标签云就有新的标签飞入，配合拼图进度亮起。

## 15. 验收标准

1. 用户不选择课程时，也能产生和使用全局画像、会话画像。
2. 用户选择不同课程时，各课程画像独立更新，不互相污染。
3. 课程测验结果只更新对应课程画像，除非跨课程证据足够。
4. 用户在无课程模式生成资源时，资源默认不绑定课程，但可后续归档。
5. `/learning-profile` 至少支持全局画像和课程画像两类展示。
6. 每个画像标签应有来源、更新时间和置信度。
7. 用户可以纠正画像，纠正结果优先级高于系统推断。
8. AI 回答、资源生成、路径推荐和资源推荐都能读取有效画像上下文。
9. 画像抽取主路径应优先使用 schema-based LLM 抽取和课程概念表匹配。
10. 规则抽取只作为兜底，不能作为长期主力抽取方案。
