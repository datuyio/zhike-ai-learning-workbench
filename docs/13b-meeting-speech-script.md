# 项目启动会演讲稿

> **对照 docs/12-meeting-presentation.md 使用**
> **主讲人**：队长
> **时长**：约 45-60 分钟
> **语气**：正式、自信、有条理

---

## 开场白（2 分钟）

大家好，欢迎参加我们「挑战杯·揭榜挂帅」项目的启动会。

今天这个会的目的很明确：

第一，跟大家讲清楚我们为什么要参加这个赛题、为什么选计算机与人工智能这个学科；
第二，让大家了解当前项目的全貌——我们已经有什么、还需要做什么；
第三，把每个人的分工、怎么协作、怎么提交代码讲透；
第四，明确最后的提交物和我们的目标分数。

整个过程大概 45 到 60 分钟，中间有疑问可以随时提。

---

## 第一部分：为什么选择计算机与人工智能学科（5 分钟）

我们先从第一个问题开始：为什么选这个学科？

### 翻到 1.1 学科选择背景

我们的赛题是科大讯飞发布的「面向一流学科建设的学科垂类大模型与创新应用开发」。

注意「学科垂类」这四个字——这意味着我们不能做一个通用的 AI 助手，而要聚焦在**一个具体的学科领域**做深做透。

那为什么是计算机与人工智能？三个原因。

**第一个原因：团队优势最大化。**

在座每个人都来自计算机/AI 相关专业。我们已有的课程资料、代码积累、对机器学习深度学习的理解，都是现成的。选其他学科意味着我们要从头学习领域知识，这个成本我们不必要花。

**第二个原因：比赛评分最有利。**

大家看这张表——技术先进性、技术实现度、内容质量度这三个大分项，加起来 50 分。代码沙箱、AI 编程辅导、学科大模型微调，这些都是计算机学科的天然特色。选数学、选物理，都不可能有这种展示效果。

**第三个原因：演示效果最有冲击力。**

评委看演示的时候，什么最抓眼球？现场写代码、运行、AI 纠错——代码沙箱一展示，评委就知道我们的技术深度。多智能体可视化、文字+代码+图解混合输出，这些都是加分利器。

### 翻到 1.2 学科知识体系

我们的知识库覆盖机器学习、深度学习、计算机科学基础、AI 工具与框架四大板块。这些课程的教材和开源资料我们已经整理好了，后面会详细讲。

## 第二部分：项目现状与进度（8 分钟）

### 翻到 2.1 双端口架构

现在看项目整体架构。我们是双端口设计：

助学端是学生端，提供 AI 对话、学习路径、画像、评估、编程实操等功能。
助教端是教师端，提供备课、批改、学情诊断、班级管理等功能。
两个端口共享同一个后端底座——AI 编排引擎、RAG 知识库、多智能体协作系统。

这个设计本身就是一个得分点，因为它体现了「商业化潜力」——换一套学科知识库就能复制到其他学科。

### 翻到 2.2 已完成功能

来说说我们手上已经有什么。

这里列了 9 个已完成模块：账号权限、AI 对话舱、资源生成、ArtifactCanvas 预览、学习路径、三层画像、在线测评、前端路由、助教端基础页面。

这些都是已经跑通的，**不需要从零开发**。我们的任务是在这个基础上做增强和新增。

### 翻到 2.3 待开发功能

红色标记的是最高优先级的——都是比赛核心得分点，也是评委最看重的功能。

特别是：多模态智能辅导、代码沙箱、AI 代码辅导、智能备课、作业批改、学情诊断。这些是我们要集中火力攻下的山头。

## 第三部分：团队分工（10 分钟）

### 翻到 3.1 组织架构

现在说分工。我们分三个队：

**A队是开发核心**，负责助学端——学生用的那一端。
**B队是开发辅助**，负责助教端——老师用的那一端。
**成队负责文档和成果**——比赛不只交代码，文档和 PPT 占很大比重。

### 翻到 3.2 各队职责

我一个个说。

**A队——助学端：**

队员b 是后端主力。你的核心产出是：多模态辅导 API、学习行为引擎、代码沙箱后端、LoRA 微调模型。你是 AI 能力的核心实现者。

队员c 是前端主力。你的核心产出是：对话舱改造、代码沙箱 UI、画像证据链展示、Agent 可视化。你是用户体验的核心实现者。

我的角色是队长，不参与编码，但负责架构决策、代码审查、进度管理和文档终审。代码质量我把关，进度我跟踪，有什么需要决策的找我。

**B队——助教端：**

副队长d 是助教端后端 + 辅助管理。你的核心产出是：备课 API、批改 API、学情诊断 API、班级管理 API。当我不在的时候，你代理管理。

队员e 是助教端前端。你的核心产出是：工作台首页、备课页面、批改页面、学情看板、班级页面。

**成队——文档与成果：**

成员f 是文档总负责。系统说明书、比赛 PPT、伦理声明、效果报告——这些比赛提交物你来统筹。

成员g 辅助成员f，负责测试用例、素材截图、合规检查。

### 翻到 3.3 八周时间线

看这张时间线图。第1周是基建和熟悉项目。第2到4周是集中开发期。第5到6周是联调。第7周是测试修复。第8周是打包提交。

注意看，成队的工作贯穿全程——不是最后一周才开始写文档的。从第2周开始就要积累素材，和开发同步进行。

## 第四部分：工作流程与规范（10 分钟）

这部分非常重要，请大家认真听。流程规范直接影响我们能不能高效协作。

### 翻到 4.1 代码协作流程

左边是队员的开发流程，右边是我的审查流程。

**队员流程：**
第一步，git pull origin develop 拉取最新代码。
第二步，git checkout -b 创建功能分支。
第三步，开发、本地测试。
第四步，git add、git commit、git push。
第五步，在 GitHub 创建 Pull Request。
第六步，@队长a 请求审查。

**我的流程：**
收到 PR 后检查代码质量，通过就合并到 develop，不通过就提修改意见。

### 翻到 4.2 分支命名规范

这里的关键是分支名要有规律。看这张表：

feat/backend/xxx —— 队员b 用
feat/frontend/xxx —— 队员c 用
feat/backend-ta/xxx —— 副队长d 用
feat/frontend-ta/xxx —— 队员e 用
feat/docs/xxx —— 成员f 用
feat/docs-aux/xxx —— 成员g 用
fix/xxx —— 任何人都可以用来修 Bug

按这个规范来，我看 PR 的时候一眼就知道谁改了什么。

### 翻到 4.3 核心规则

四条规则，请大家记住：

**规则一：禁止直接 push develop。** 所有代码必须走 PR + 审查。谁要是直接 push develop，我会请他重来。

**规则二：API 契约先行。** 前端不等后端。开发前，后端队员先把 API 的请求和响应格式定义好，前端用 Mock 数据开发。等后端写完了，再替换成真实 API。这样前后端能并行开发，不浪费时间。

**规则三：每日站会。** 每天早上 15 分钟，就在群里说三个问题：昨天做了什么、今天要做什么、有什么阻塞。不要长篇大论，简短有力。

**规则四：代码审查。** 我审查 PR 时会检查四个点——能不能正常运行、代码风格合不合理、注释是不是中文、有没有泄露敏感信息。

## 第五部分：资料来源（5 分钟）

### 翻到 5.1 知识库构建

我们知识库的构建路线是这样的：

教材 PDF 经过向量化存入向量数据库，AI 回答时通过 RAG 检索相关知识。同时，开源资源经过 QA 提取变成微调数据，用来做 LoRA 微调。

这样两条腿走路：RAG 保证回答的准确性和可溯源，LoRA 微调保证回答的学科专业性。

### 翻到 5.2 微调训练数据

LoRA 微调需要三部分数据：

5000 条以上的学科 QA 对，从教材里提取。
2000 条以上的教学案例对，模拟教案和批改场景。
1000 条以上的代码示例对，做代码辅导微调。

队员b 负责这份数据的整理和微调工作。

## 第六部分：成果提交（5 分钟）

### 翻到 6.1 比赛提交物

比赛要交的东西不少，大家看这张表：

### 翻到 6.2 GitHub 仓库结构

我们的 GitHub 仓库分这几个目录：README、backend、frontend、docs、scripts、docker-compose。

README 必须写好搭建步骤，让评委能一键跑起来。docs 目录放所有文档。

## 第七部分：评分对标与目标（3 分钟）

### 翻到 7.1 目标分数

这张表是我们的评分对标。7 个评分项，满分 100+10。

我们的目标是 89 到 95 分，争取加分到 100+。

拿分策略很清晰：
作品完成度——双端口完整闭环。
创意实用度——聚焦真实学习场景。

技术先进性——LoRA 微调 + 多模态。
内容质量度——学科知识库 + 防幻觉 + 引用溯源。
商业化潜力——双端口可复制。
用户认可度——真实用户试用。

## 第八部分：答疑与总结（5 分钟）

### 翻到 Q&A

常见问题我这里先回答一下：

**开发环境怎么搭？** README 和 docs/12b-team-onboarding-guide.md 有详细步骤。

**遇到问题找谁？** 后端找队员b 或副队长d，前端找队员c 或队员e，架构问题找我。

**怎么确认进度？** 每天站会 + GitHub Projects 看板。

**代码提交注意事项？** 不要直接 push develop，必须走 PR。

### 特别提醒

最后强调五个成功关键：

第一，API 契约先行——前后端约定好再各自开工。
第二，每日同步——15 分钟站会，早暴露问题早解决。
第三，不要拖到最后才联调——第5到6周联调是死线。
第四，文档同步跟上——功能做完，成员f 马上更新文档。
第五，代码注释用中文——这是项目规范，大家都遵守。

我们有一个好的项目基础，有清晰的分工，有规范的流程，有明确的目标。

剩下的就是——动手干。

有什么问题现在可以问，没有的话我们就开始干活了。
